# SPEC-009：dsh 单轮轮询挂死会让监控静默停摆

> 状态：done
> 类型：bugfix
> 需求来源：用户 2026-10-20 反馈「网页端的 dsh 明明在运行但是指示灯没亮」
> 基线提交：`dbca9cf`；Windows 11；Chrome 139；桌面端 dsh 0.2.1-rc.2
> 需求依据及假设：用户期望 dsh-web 在远端确有会话运行时亮蓝。不改既有状态语义，只让"挂死"变成"可恢复 + 有日志"。
> 关联/替代条款：补齐 SPEC-002/AC-01 与 SPEC-005 的生命周期缺口。

## 1. 问题复现与根因

现象：网页端（`127.0.0.1:13080`，SSH 隧道到远端 dsh）在跑任务，指示灯的 `web 13080` 那行不亮。

取证：
1. 灯进程从 2026-10-19 17:46:51 一直运行；今天（10-20）日志 1423 行里**只有扩展每 30 秒的自报**，**没有任何 dsh 日志**。
2. 昨天 17:47:12 之后再也没有「已从 chenjunming@10.104.70.7 取回密钥」——而远端密钥缓存只有 30 分钟，正常每 30 分钟必刷新一次。也就是说 **dsh-web 的监控在 17:47~18:17 之间就不再轮询了**。
3. 用仓库代码复现远端链路：第一轮 401 → 取远端密钥 → 第二轮 `ok, 68 会话, idle`；随后直接连远端采样，11:05:42–11:05:52 为 `running: 1`，11:08:43 之后又出现 `running: 1` —— **远端 API 的 running 标记是正常的**，问题在灯这一侧。
4. 重启指示灯后立刻恢复：11:07:52 401 → 11:08:12 取回密钥 → 浮窗恢复可见。

根因：`DshMonitor.pollOnce()` 里 `this.polling = true` 之后，`ensureClient()`（可能走 ssh 取远端密钥）或 `listSessions()` 若**永不返回**，`finally` 永远不执行 —— 既不重排下一轮、也不记日志，监控静默死掉。远端密钥恰好是在"缓存过期后第一次 ssh 取密钥"这条路径上挂住的，所以卡在 17:47 之后的第一轮刷新。

## 2. 范围与非目标

- 包含：`DshMonitor` 增加单轮看门狗（默认 120s，可注入）；触发时 warn + 释放 `polling` + 立即排下一轮；单元测试；规格与索引。
- 不包含：ssh 自身的超时策略（已有 15s 硬超时）；sqlite/codex 监控的同类看门狗（未观察到同类事故，另立规格）；UI。

## 4. 方案与任务切片

单切片，测试先行：`pollOnce()` 里用 `setTimeout` 武装看门狗（`unref`，完成后清理），超时回调里 `polling=false`、`failureCount+=1`、warn、`scheduleNext()`；`finally` 里若看门狗已接管就不再重复排程。阈值可通过 `DshMonitorOptions.pollWatchdogMs` 注入（测试用 80ms）。
