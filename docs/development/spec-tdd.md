# specTDD 开发流程

本项目将 specTDD 定义为 **Specification + Test Driven Development**。从本次整理之后的变更开始执行；已有实现不补造历史 Red 记录。

## 一次迭代的单位

一份 `docs/specs/NNN-<slug>.md` 描述一个边界清晰、能独立验收的变更。使用[模板](../specs/_template.md)，在[索引](../specs/README.md)分配下一编号。验收条件使用 `AC-01` 等局部编号，引用时写全 `SPEC-NNN/AC-01`。相互独立的需求拆开；一个验收条件可对应多个测试。

需求从用户任务、已确认规格或缺陷证据中提取。先写目标行为，再写实现计划。现有明确授权直接记录为来源；不为了流程增加重复确认。会改变产品语义、数据兼容或无法合理推断的关键未知项才需询问，独立的调查和准备可以继续。

## 阶段与关卡

| 状态 | 必须完成的工作 | 退出条件 |
| --- | --- | --- |
| `draft` | 复现/调研、需求来源、范围、G/W/T、边界异常、影响和测试计划 | 验收条件可观测；关键疑问已解决；计划覆盖风险 |
| `ready` | 记录需求依据、假设、规格版本及基线结果 | 可开始某个验收切片的测试，不存在依赖的未知项 |
| `implementing` | 每个切片依次 Red → Green → Refactor，更新追踪表 | 全部目标行为有测试或有理由的真机验收，新增测试通过 |
| `verifying` | 全量回归、构建、smoke、相关 Windows/真实服务验证、文档同步 | 达到下述完成门槛，证据足够复核 |
| `done` | 记录交付结果、兼容性、残留问题和提交引用 | 无待验收的目标条件，索引同步 |
| `blocked` | 记录具体前置、已完成工作、恢复步骤和阻塞前状态 | 前置满足后返回相应状态，重新验证受影响步骤 |

状态写在规格文件和索引中。`ready` 表示需求可执行，不声称用户已评审某份文档；`done` 表示本变更完成，不代表已发布。范围/预期改变时先修改规格和测试计划，再继续实现；保留变更缘由。

## Red → Green → Refactor 的证据

1. **Red**：为一个 AC 写最小、有区分能力的测试。在未实现目标行为的代码上运行，记录失败断言和原因。缺依赖、导入失败、编译错误、服务未启动或已有失败不能充当 Red；先排除这些问题。缺陷修复优先使用能重现原问题的回归测试。
2. **Green**：只实现让该切片通过所需的改动，运行目标测试和相邻回归，记录结果。测试断言应表达规格，不与实现一起迁就错误结果。
3. **Refactor**：在 Green 后整理结构，保持外部行为，重跑目标及受影响测试；没有必要重构时写“无必要”。继续下一个 AC。

每条记录包含命令、工作目录、代码提交/工作区状态、测试路径和用例名、预期与实际、退出码。可附脱敏日志或 CI 链接；不要求把整个输出塞进规格，也不要求机械地每步提交。Red 和 Green 的对应版本必须可辨认，不能事后把既有失败描述成自己新增的测试。

纯重构先补足能约束外部行为的特征测试并在原代码通过，再重构并回归；原代码已符合行为时记录 Red 不适用，不故意制造失败。纯文档、格式、机械修改如不改变运行行为，说明例外原因并做相关一致性检查；涉及行为的部分仍遵循正常流程。

## 测试计划与追踪

每个 AC 都填写“测试文件/用例或真机步骤 → Red → Green → 回归结果”。涉及监控器须考虑成功、超时/断连/畸形输入、重试、停止清理、去重和恢复；只选择与变更相关的风险，不能只测正常路径。涉及 UI/窗口/系统权限时，纯函数或 mock 之外还须列真机步骤。

本项目命令与平台要求见[测试与验收](testing.md)。一次全量回归不能替代切片 Red；若没有代码改动，已有基线失败也不能算本轮 Red。

## 完成门槛（DoD）

- [ ] 需求有依据，范围和所有 AC 明确，关键疑问已关闭。
- [ ] 所有 AC 已验收，测试/真机证据与对应实现可追踪；TDD 例外有适用理由。
- [ ] 类型检查、全量测试、构建后 smoke 已执行，退出码与实际通过/失败/跳过/未运行均已记录。
- [ ] 无新增失败、无目标路径或受影响路径的未解决失败；没有删断言、隐藏失败或伪造全绿。
- [ ] 涉及 Windows GUI、PowerShell、通知、焦点、打包或外部服务的 AC 已在相应环境验收。没有环境就保持 `verifying`/`blocked`，不得写 `done`。
- [ ] 规格索引、配置/接口说明、用户文档及相关设计理由已更新，未提交本机配置或凭据。
- [ ] 交付说明列出 Spec ID、变更、验证证据、已知限制、发布状态；发布另按用户授权执行。

接管时的[基线失败](baseline-validation.md)保留为历史证据；后续收敛结果以对应 Spec 为准。默认要求全绿；若本轮仅影响无关路径，可在提交回归对比后，由用户或维护者明确接受**具体的既有失败及原因**才将行为变更标为 `done`。没有这项依据则保持 `verifying`。纯文档整理可在文档检查通过、基线如实记录后结束，不声称应用验证通过。

## 评审与执行

评审看“需求是否说清 → 测试是否能抓住错误 → 实现是否满足规格 → 真实环境是否已验收”，不能仅凭测试数量或编译成功判定交付。规格草案可以先提交评审，不等于允许未经规格/Red 的实现。

当前仓库没有 CI 工作流或自动规格状态检查。`AGENTS.md`、规格追踪表和本页是人工/AI 执行约定；如需自动关卡，另建迭代规格并测试，不在本轮顺带改构建配置。
